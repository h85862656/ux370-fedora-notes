# 04. 1TB SSD 磁碟空間調整（雙系統）

**狀態**：進行中 In Progress
**認領視窗**：2026-10-15 / SSD 磁碟空間調整

**⚠️ 這項具有破壞性、資料遺失風險高，所有子項開始前必須先完成 04a 的備份要求，任何一個視窗處理這項都要再次跟使用者確認已經備份完成，才能繼續往下做。**

子項需要**依序**處理（b→c→d→e→f 有先後依賴關係），**不建議拆給多個視窗同時做**，避免互相干擾同一顆硬碟的分割表——建議整個項目 04 從頭到尾由同一個視窗認領處理完。

**起因（2026-10-15）**：Fedora 根目錄只剩 818 MB，持續跳出空間不足警告，使用者要求直接進行分割調整（明確表示不做暫時性的清理騰空間）。

全碟實際使用量合計約 **175 GB**。

Fedora 的 `/` 和 `/home` 共用同一個 btrfs 分割區（subvol `root` 與 `home`），所以系統與個人檔案互相搶空間。

### 關鍵結論 1：p8 在硬碟最尾端，後面沒有任何空間

p8 結尾在磁區 1953523712，硬碟總共 1953525168 磁區，中間只差 1456 個磁區（約 728 KB），那是 GPT 備份標頭的位置。

**所以「直接往後擴大 Fedora」這條路不存在**，空間一定要從左邊的 p5 挪過來。但 p5 與 p8 之間卡著 p6（RECOVERY）和 p7（`/boot`），這兩個必須先往左搬，而 `/boot` 與 `/` 在系統運行中是掛載狀態，**無法在運行中的系統上搬動 → 需要 Live USB**。

### 關鍵結論 2：資料槽幾乎是空的，不需要縮小 NTFS

p5 有 601 GB，實際只用 3.1 GB（0.5%）。使用者確認**內容可以全部清空**。

因此原本 04b 規劃的「縮小 NTFS」改成**刪除後重新建立**。這是本項目最大的風險降低——原地縮小一個裝著資料的 644 GB NTFS 是整個工程最危險的操作，而刪除＋新建一個空的 NTFS 幾乎沒有風險，`ntfsresize` 完全不需要執行。

⚠️ **清空前的陷阱**：p5 裡面有 `OneDrive`（1.3 GB）和 `SynologyDrive`（299 MB），這兩個是**雲端同步資料夾**。直接刪除會把刪除動作同步到雲端，連雲端副本一起刪掉。**必須先在 Windows 的用戶端解除連結／停止同步，確認用戶端不再管理該資料夾之後，才能刪本機檔案。**

### 關鍵結論 3：Windows 系統槽的 NTFS 不一致

`ntfsresize --info --no-action /dev/nvme0n1p3` 回報：

```
Cluster accounting failed at 18304877 (0x1174f6d): missing cluster in $Bitmap
...
Filesystem check failed! Totally 71 cluster accounting mismatches.
ERROR: NTFS is inconsistent. Run chkdsk /f on Windows then reboot it TWICE!
```

**2026-10-16 更新：已修復。** 使用者在 Windows 執行 `chkdsk C: /f` 並重開機後，複查確認 71 處錯誤全部消失，`ntfsresize --info` 現已可乾淨讀取 p3，實際使用 149 GB（46.5%）。

本項目的方案**不會動到 p3**，所以這不是硬性阻擋，但它顯示這顆硬碟上的 NTFS 曾經沒有乾淨卸載過（通常是 Windows 快速啟動／休眠造成）。動分割表之前應先在 Windows 執行 `chkdsk C: /f` 並**重開機兩次**（第一次只是排程檢查，第二次才真正完成）。

### 其他環境事實

- **沒有 BitLocker**：`lsblk` 把 p3、p5 認成單純的 `ntfs`（若有加密會顯示 `BitLocker`）。省掉「動分割表後需要恢復金鑰」這個常見大坑。
- **只有 p1 沒有 1 MiB 對齊**：p1 起始於磁區 34（GPT 標頭後第一個可用位置），現代工具都從磁區 2048 起算；p2～p8 全部對齊。這台曾經用 Acronis 的 `.tib` 整碟轉移到另一顆 SSD，這個混合樣貌可能是當時留下的。屬於 04d 的範圍，不急、也不影響效能（MSR 區內沒有檔案系統）。
- **RAM 15 GB**：04f 休眠需要約 16 GB 的 swap，規劃 Fedora 容量時要算進去。目前只有 zram 8 GB，**沒有實體 swap**，所以現在不能休眠。
- p4 與 p5 之間有一塊 2.1 MB 的可用空間，無影響。

## 施工方案（2026-10-15 決定）

| | **方案 A：搬動分割區（採用）** | 方案 B：btrfs 多裝置 |
| --- | --- | --- |
| 做法 | 刪 p5 → p6、p7 往左搬 → p8 擴大到 100 GB → 剩餘空間重建資料槽 | 刪 p5 → 在空出的位置建新分割區 → `btrfs device add` 併入 Fedora |
| 搬動資料量 | 約 3 GB（p6+p7），很快 | 0 |
| 需要 Live USB | 要 | 不用，線上即可 |
| 最終版面 | 乾淨，Fedora 是一塊連續的 100 GB | Fedora 空間分散在兩塊不相鄰的分割區 |
| **休眠（04f）** | 可以 | **不行** |

**選擇方案 A。** 決定性理由是 **btrfs 在多裝置模式下不支援 swapfile**，方案 B 會直接讓 04f 休眠做不成（除非另切獨立 swap 分割區，但那又繞回要動分割表）；而且空間分散兩塊會讓未來接手的人困惑。多一支 Live USB 換乾淨版面與可用的休眠，划算。

容量規劃（**實際數字待 04b/04c 動工前最終確認**）：p5 釋出 601 GB → Fedora 取約 70 GB（29 → 100 GB）→ 資料槽重建約 500 GB，其餘保留未配置或併入資料槽。

**備份層次（三層，缺一不可）**：

| 層 | 內容 | 擋住的失效模式 |
| --- | --- | --- |

**容量評估**：外接硬碟 500 GB，全碟實際使用約 175 GB，Acronis 對 NTFS 只備已用區塊且會壓縮（btrfs 不認識，會逐磁區複製那 30 GB）。映像檔預估 **120～160 GB，500 GB 綽綽有餘**，不需要取捨。

**備份流程**：

1. 先清空資料槽（**務必先解除 OneDrive / Synology Drive 同步**）→ 映像更小更快
2. 開 Windows → Acronis → **整個磁碟備份**（不是只備 C:）→ 存到外接硬碟
3. 備份後**執行 Acronis 的「驗證備份」**，這步不可省
4. 回 Fedora 做第 1 層分割表快照與第 3 層 `/home` 複製

**施工前 Windows 端前置作業（必須由使用者操作，Fedora 端無法代勞）**：

- **只關閉「快速啟動」，保留休眠與睡眠**（控制台 → 電源選項 → 選擇電源按鈕的功能 → 變更目前無法使用的設定 → 取消勾選「開啟快速啟動」）
  - ⚠️ **不要執行 `powercfg /h off`**（本檔案 2026-10-16 以前的版本這樣寫，是錯的）。使用者有在使用 Windows 的休眠與睡眠，而該指令會把休眠一併關掉。
- 執行 `chkdsk C: /f`，**重開機兩次**（第一次只是排程檢查，第二次才真正完成）

### 為什麼只需要關快速啟動

三件常被混為一談的事要分開看：

| | 是什麼 | 風險 |
| --- | --- | --- |
| 睡眠 Sleep | 記憶體保持通電，磁碟狀態不變 | 無。而且無法從睡眠直接開 Fedora，一定要先喚醒 |
| 休眠 Hibernate | 寫入 `hiberfil.sys` 後斷電 | 有，但可控——是使用者主動選的，自己知道 |
| 快速啟動 Fast Startup | **偽裝成關機的休眠** | 危險——按下「關機」以為關了，其實處於休眠狀態 |

危險只來自第三個，因為它製造了「我以為硬碟已經乾淨卸載」這個錯覺。

**要記住的規則：Windows 休眠之後，不要直接開 Fedora 去掛載那顆 NTFS。** 要先喚醒 Windows、正常關機，再開 Fedora。睡眠不必擔心，因為本來就無法跳過喚醒直接開另一個系統。

### 髒旗標為什麼會造成檔案系統損壞（機制）

NTFS 用兩本帳記錄空間配置，兩本必須對得起來：`$Bitmap` 是一張位元表，每個位元代表一個叢集（4 KB），1 = 已占用；`$MFT` 是每個檔案的記錄，寫明自己佔了哪些叢集。正常情況下，MFT 裡所有檔案聲稱佔用的叢集，在 `$Bitmap` 裡都應該是 1。

Windows 為了效能，把 NTFS 的中介資料大量快取在記憶體裡、不即時寫回磁碟。快速啟動的「關機」是把核心狀態（**包含那些還沒寫回磁碟的快取**）存進 `hiberfil.sys`，因此**磁碟上的 `$Bitmap` 與 `$MFT` 是過期的**。接下來：

1. 開 Fedora 掛載該 NTFS → 讀到的是那份過期帳本
2. 在 Fedora 寫入檔案 → 依過期的 `$Bitmap` 找空位、配置叢集、更新磁碟上的帳本
3. 開回 Windows → 從 `hiberfil.sys` 還原記憶體裡那份舊帳本，蓋掉磁碟上的版本
4. Windows 完全不知道 Fedora 動過什麼

結果兩本帳對不起來：Fedora 配置出去的叢集在 Windows 眼中是空的，可能再配給別的檔案（兩個檔案共用同一塊空間、互相覆蓋）；或者某個檔案的 MFT 聲稱佔用某叢集，但 `$Bitmap` 說那格是空的——也就是本項目實際觀測到的 `missing cluster in $Bitmap`。

⚠️ **上述機制後來被證實不是本機 71 筆錯誤的成因**，保留這段說明是因為機制本身正確、而且「Windows 休眠後不要開 Fedora 掛載 NTFS」這條規則仍然成立。成因的最新結論見下方「71 筆錯誤的成因追查」。

### 71 筆錯誤的成因追查（2026-10-16）

**快速啟動已排除。** 在 Windows 端查證：登錄檔 `HiberbootEnabled = 0`，`powercfg /a` 回報「快速啟動：已在目前的系統原則中停用此動作」——這台機器的快速啟動本來就是關的，而且休眠功能保留可用，正好就是本項目建議的配置，使用者不需要做任何更動。

因此原先「71 筆錯誤八成源自快速啟動」的推論**不成立**。重新評估：

| 可能成因 | 評估 |
| --- | --- |
| 快速啟動 | ❌ **排除**——查證為一直關閉 |
| 硬體／SSD 故障 | ❌ **排除**——SMART 的 `Media and Data Integrity Errors` 為 0，SSD 從未回傳損壞資料 |
| 不乾淨斷電 | ⬆️ **主要嫌疑**——SMART 顯示 `Unsafe Shutdowns: 174`，佔 1297 次開關機的 13.4% |
| 從 Fedora 寫入 NTFS | ⬆️ 可能。Fedora 44 預設使用核心的 `ntfs3` 驅動，其寫入實作歷來有過帳目相關的 bug |
| Windows 主動休眠後被 Fedora 掛載 | 可能——與快速啟動同一個機制，只是由使用者主動觸發 |
| 當年的 Acronis 整碟轉移 | 可能，但時間久遠，無法查證 |

⚠️ **NVMe 對「不安全關機」的認定很寬鬆**：只要控制器沒收到正常的關機通知就計入，當機、強制斷電、甚至某些驅動在重開機或休眠時的行為都可能被記成一次。**174 不等於真的硬關機 174 次**，只能說明方向落在「關機／斷電流程沒走完」這一類，而不是硬體故障。

**實務結論（重點已移位）**：危險不在關機設定，而在**從 Fedora 寫入 NTFS**。建議重建後的資料槽在 Fedora 端盡量只讀不寫；確實需要寫入時，使用 `ntfs-3g`（使用者空間驅動，行為較保守）而非核心的 `ntfs3`。

**p5 清空說明（已結案）**：p5 裡原有的 `桌面`（1.2 GB）是 **OneDrive「已知資料夾移轉」** 把 Windows 桌面重導向到 D 槽留下的。使用者已在 Windows 端清除 OneDrive 的殘留設定並刪除該資料夾——這一步是必要的，因為只要殘留設定還在，Win11 即使沒有安裝 OneDrive 程式，仍會持續連回 D 槽重建該資料夾，分割區刪掉後它還是會再長出來。

目前 p5 只剩 `$RECYCLE.BIN`（128 MB）、`System Volume Information`（45 MB）、`__Previews`（8 KB），使用量 1603 MB（0.2%），**確認完全可丟棄**。

**04b 方案定案：維持「刪除重建」**（曾評估改為「縮小 p5」以保留桌面資料夾，但該資料夾已確認可刪，刪除重建更乾淨，可一併清掉 `$RECYCLE.BIN` 等殘留，得到全新的 NTFS）。

## 04c. Fedora 自己的空間調整到 100GB

**進度與發現（2026-10-15）**：需要 Live USB。p8 位於硬碟最尾端、後方無空間，必須先把 p6（823 MB）與 p7（2 GB `/boot`）往左搬到 p5 釋出的空間，讓空缺與 p8 相鄰後才能擴大。搬動資料量僅約 3 GB。

## 資源佔用（CPU / RAM / 續航）

本項目調整的是磁碟空間配置，**不新增任何常駐程式、服務或計時器**，因此對 CPU 與 RAM 沒有影響。

- **CPU**：0。分割調整是一次性操作，完成後沒有任何東西持續執行。
- **RAM**：0。同上。
- **續航**：**預期略為改善。** 兩個原因：(1) 目前磁碟 98% 滿，btrfs 在接近全滿時配置區塊的成本上升、也無法有效做 discard/trim，空間充裕後寫入行為更有效率；(2) 04f 的休眠完成後，長時間不用可改用休眠取代待機，待機每小時仍有數瓦耗電，休眠則幾乎為零。
- 休眠會佔用約 16 GB 磁碟空間作為 swap——這是磁碟成本，不是 CPU/RAM/耗電成本。

## 附錄：備份工具比較（2026-10-15 評估）

| | Acronis（採用） | Clonezilla |
| --- | --- | --- |
| 在這台的實證 | **有**：曾用 `.tib` 整碟還原到另一顆 SSD 並成功開機 | 無 |
| btrfs（Fedora 那槽） | 不認識 → 逐磁區複製，映像較大 | 認得（partclone）→ 只複製已用區塊 |
| NTFS | 只備已用區塊、支援壓縮與 VSS | 認得（partclone） |
| GPT + EFI + 全分割區一次備份 | 可以 | 可以 |
| 映像驗證 | 有 | 有（check image） |
| 費用 | 需授權（使用者已有） | 免費 |
| 介面 | Windows 圖形介面 | 文字選單式 Live USB |

**原本的初步建議是 Clonezilla**，理由是它對 btrfs 是檔案系統感知、映像較小，而且第二階段本來就要開 Live USB、工具鏈一致。

**改採 Acronis 的理由**：得知這台曾用 Acronis 完成整碟轉移後，判斷「已在本機實證過還原成功」的價值高於「映像檔較小」。對 btrfs 的疑慮本質上是效率問題（映像較大），不是正確性問題（還原不回來），而後者已被實際經驗排除。外接硬碟 500 GB 對 120～160 GB 的映像綽綽有餘，映像大小在這裡不構成限制。

**若將來 Acronis 授權失效或不可用**，Clonezilla 是等效的替代方案，但屆時屬於「未在本機驗證過的路徑」，建議先做一次還原測試（例如還原到另一顆硬碟）再信任它。
